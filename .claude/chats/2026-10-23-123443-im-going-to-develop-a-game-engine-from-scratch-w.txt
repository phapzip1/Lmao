● Game Engine Plan: C++ / Vulkan / GLFW

  1. Initial Architecture

  Guiding principles

  1. Strict layering. A lower layer never includes headers from a higher one.
     This one rule keeps a 13-subsystem engine from turning into spaghetti.
  2. Handles, not pointers. Every resource, entity and asset is a 32/64-bit
     handle with an index and a generation counter. Stale handles get caught
     instead of becoming use-after-free bugs. This matters a lot once scripting,
     streaming and networking all hold references.
  3. Data-oriented core. Use ECS for gameplay data. The "scene graph" is a
     transform hierarchy built on top of the ECS, not a deep Node* tree.
  4. Every subsystem is a job producer. Nothing owns a thread except the main
     thread (GLFW needs it), the audio thread, the IO thread and the network
     thread.
  5. Write it yourself where you learn something, use a library where you don't.
     Building a PNG decoder from scratch teaches you nothing about engines.

  Core subsystem decisions

  System: Memory
  Recommendation: Global-new hooks with tagged tracking per subsystem.
  Allocators: frame linear allocator (double-buffered, reset each frame), pool
  allocators for fixed-size objects (components, nodes), TLSF for general heap
  use, and stack/scoped arenas for loading. Add guard bytes and poisoning in
  debug builds.
  ────────────────────────────────────────
  System: Threads / jobs
  Recommendation: Work-stealing job system with N−1 workers and a counter-based
  wait (WaitForCounter). Start without fibers and add them later if you need
  them. Use a frame graph: Input → Script → AI → Physics(fixed) → Anim →
  Transform update → Render extract → Render submit.
  ────────────────────────────────────────
  System: Frame model
  Recommendation: Fixed-timestep simulation (e.g. 60 Hz) with interpolation for
  rendering. Render runs one frame behind the simulation: extract a render
  snapshot, then record it in parallel while the next sim frame runs.
  ────────────────────────────────────────
  System: ECS
  Recommendation: Archetype- or sparse-set-based (sparse-set is easier to
  write).
  Components are POD where possible. Transform + Parent + Children components
  form the scene graph. Dirty-flag propagation runs in a topologically sorted
  pass.
  ────────────────────────────────────────
  System: Reflection
  Recommendation: A macro- or codegen-based reflection system early on. It is
  what makes serialization, the editor inspector, script bindings and network
  replication cheap to write. This is one of the highest-leverage things you
  can build.
  ────────────────────────────────────────
  System: Resources / streaming
  Recommendation: An asset DB with GUIDs and a cooked binary format (an offline
  cooker converts glTF/PNG/WAV into engine-ready blobs). Asset states go
  Unloaded → Loading → Loaded → Resident(GPU). A dedicated IO thread does async
   reads, and a transfer queue does GPU uploads. Ref-counted handles plus a
  priority queue drive streaming (distance, screen size).
  ────────────────────────────────────────
  System: Physics
  Recommendation: Write your own: BVH broadphase, SAT/GJK+EPA narrowphase,
  sequential-impulse solver with warm starting, sleeping, and CCD for fast
  bodies. Keep the API narrow (PhysicsWorld, Body, Shape, queries) so you could
   swap in Jolt later if your own solver hits a wall.
  ────────────────────────────────────────
  System: Audio
  Recommendation: Use miniaudio for device output only. Write your own mixer,
  voices, buses, DSP (low-pass, reverb) and 3D spatialization (panning plus
  distance attenuation, and HRTF later). The audio thread communicates through
  lock-free ring buffers only.
  ────────────────────────────────────────
  System: Animation
  Recommendation: Skeleton, clips (compressed keys), sampling, a blend tree
  (1D/2D blend spaces), a state machine with transitions, two-bone IK, root
  motion. GPU skinning via a storage buffer of joint matrices.
  ────────────────────────────────────────
  System: Scripting
  Recommendation: Lua 5.4 or LuaJIT with sol2 bindings, generated from your
  reflection data. Scripts only ever see entity handles. Hot reload by file
  watching. Run scripts in a deterministic phase, never inside jobs at first.
  ────────────────────────────────────────
  System: AI
  Recommendation: Behavior trees with a blackboard, utility AI later, navmesh
  generation via Recast/Detour (or your own once you understand it), A* with a
  time-sliced path request queue, and a perception system (sight cones, hearing
   events).
  ────────────────────────────────────────
  System: Networking
  Recommendation: UDP with your own reliability layer (sequence numbers, ack
  bitfields, channels). Client-server authoritative model, snapshot replication
   with delta compression, client-side prediction and reconciliation,
  interpolation of remote entities. Mark replicated fields through reflection.
  ────────────────────────────────────────
  System: Localization
  Recommendation: UTF-8 everywhere. Use string tables keyed by ID
  ("menu.start"),
  loaded per locale, with plural and format rules. Use FreeType + HarfBuzz for
  shaping (needed for Arabic, Thai, Vietnamese diacritics and similar). Render
  MSDF font atlases for crisp scaling.
  ────────────────────────────────────────
  System: Cinematics
  Recommendation: A timeline asset made of tracks (transform, camera, animation,

  audio event, script event, property curve, subtitle). The sequencer evaluates
   them at time t and writes into the ECS. Support scrubbing in the editor, and
   make the timeline's audio sync to the audio clock.
  ────────────────────────────────────────
  System: 2D / 3D
  Recommendation: One renderer with two front-ends. 2D is a sprite batcher
  (instanced quads, texture arrays or bindless), tilemaps and an orthographic
  camera, all going through the same render graph.

  Libraries worth using (not the interesting part)

  GLFW, Vulkan SDK, volk (loader), VMA (memory), glm (or your own math), Dear
  ImGui, stb_image, fastgltf/cgltf, miniaudio, Lua/sol2, FreeType/HarfBuzz,
  Tracy (profiler), SPIRV-Reflect, DXC or glslang (or Slang). Build with CMake +
  vcpkg, using MSVC or clang-cl.

  3. Vulkan Design Decisions

  Baseline: target Vulkan 1.3

  1.3 removes most of the historic pain. Require these features:

  ┌───────────────────────────────────┬─────────────────────────────────────┐
  │              Feature              │                 Why                 │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │                                   │ No VkRenderPass or VkFramebuffer    │
  │ Dynamic rendering                 │ objects. Far simpler, especially    │
  │                                   │ with a render graph.                │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │                                   │ Saner barrier API                   │
  │ Synchronization2                  │ (vkCmdPipelineBarrier2, per-barrier │
  │                                   │  stage masks).                      │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │                                   │ One semaphore per queue tracks GPU  │
  │ Timeline semaphores               │ progress. Ideal for deletion        │
  │                                   │ queues, streaming and async         │
  │                                   │ compute.                            │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │                                   │ One global descriptor set holding   │
  │ Descriptor indexing (bindless)    │ large arrays of textures and        │
  │                                   │ buffers. Materials just store       │
  │                                   │ indices.                            │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │                                   │ Pass GPU pointers via push          │

  │                                   │ descriptors. Great for GPU-driven   │
  │                                   │ rendering later.                    │
  ├───────────────────────────────────┼─────────────────────────────────────┤

  │ where available                   │                                     │
  └───────────────────────────────────┴─────────────────────────────────────┘

  Key decisions

  1. Thin RHI, not a multi-API abstraction.
  Wrap Vulkan in engine types (BufferHandle, TextureHandle, PipelineHandle,
  CommandList), but don't design for DX12/Metal yet. The wrapper's job is
  lifetime management, handle validation and debug naming, not portability.

  2. Memory: VMA, always.
  Never call vkAllocateMemory per resource, because there's a driver limit on
  allocation count (often 4096). Use one VMA allocator and separate pools for
  streaming textures if you need budget control. Query VK_EXT_memory_budget.

  3. Frames in flight = 2.
  Each frame owns its command pools (one per thread), a linear
  descriptor/uniform upload ring, and a deletion queue. A resource is destroyed
  only once the GPU's timeline value passes the frame that last used it.

  struct FrameContext {
      VkCommandPool        cmdPools[MAX_THREADS];   // reset whole pool per
  frame
      LinearGpuAllocator   uploadRing;              // per-frame
  constants/staging
      DeletionQueue        deletions;               // freed when timeline >=
  signalValue
      uint64_t             signalValue;             // timeline semaphore value
      VkSemaphore          imageAcquired;
  };
  // Note: render-finished semaphores are per *swapchain image*, not per frame.

  4. Swapchain.
  - Use FIFO by default (guaranteed available, vsync) and MAILBOX if available
    for low latency.
  - Recreate on VK_ERROR_OUT_OF_DATE_KHR, on SUBOPTIMAL, and on GLFW framebuffer
    resize.
  - Skip rendering while the window is minimized (extent 0×0).
  - Keep one render-finished semaphore per swapchain image. This is the most
    common validation error in modern tutorials.

  5. Bindless descriptors.
  A single descriptor set at set 0 contains:
  - binding 0: sampler2D textures[]
  - binding 1: storage buffers
  - binding 2: samplers
  - binding 3: storage images

  All are flagged UPDATE_AFTER_BIND | PARTIALLY_BOUND. Per-draw data goes in
  push constants (≤128 bytes guaranteed), holding indices and device addresses.
  Use nonuniformEXT when an index varies within a draw.

  6. Shaders.
  Pick HLSL via DXC or Slang; both are better than GLSL for a large codebase.
  Compile offline in the cooker, use runtime compilation for hot reload, and
  drive pipeline layouts from SPIRV-Reflect. Persist the VkPipelineCache to
  disk, and compile pipelines on worker threads.

  7. Render graph (from M5).
  Each pass declares its reads and writes. The graph then:
  - topologically sorts the passes,
  - culls passes nobody reads,
  - inserts barriers and layout transitions automatically,
  - aliases transient memory.

  Start simple: no aliasing, single queue. Add async compute later. Doing this
  early saves you from hand-written barriers, the #1 source of Vulkan bugs.

  8. Queues.
  - Graphics+present queue: everything at first.
  - Transfer queue: streaming uploads (requires queue-family ownership
    transfers, or CONCURRENT sharing at a small cost).
  - Async compute queue: later, for culling, particles and post-processing.

  9. Multithreaded recording.
  Command pools are not thread-safe, so use one per thread per frame. Workers
  record into separate primary command buffers (or secondaries) and submit them
  in order. vkQueueSubmit2 needs external synchronization, so one thread
  submits.

  10. Conventions (fix these on day 1):
  - Reverse-Z with D32_SFLOAT: clear depth to 0, compare with GREATER. Much
    better precision.
  - Y flip via negative viewport height (core since 1.1), so your math can stay
    Y-up.
  - Right-handed world, column-major matrices. Document it in one header and
    never deviate.
  - Name every Vulkan object with vkSetDebugUtilsObjectNameEXT and wrap passes
    in vkCmdBeginDebugUtilsLabelEXT. RenderDoc becomes 10× more useful.

  11. Later: GPU-driven rendering.
  Store meshes in mega-buffers, do frustum and occlusion culling in a compute
  shader, and draw with vkCmdDrawIndexedIndirectCount. Design the bindless/BDA
  layout now so this is an extension rather than a rewrite.

  4. Difficult Debugging

  Build the debugging infrastructure first (M0–M2)

  - Validation layers in debug builds, with synchronization validation on (use
    vkconfig), and GPU-assisted validation on demand.
  - Debug-utils messenger that breaks into the debugger on errors.
  - Object names and labels on everything.
  - RenderDoc integration (in-app capture hotkey through the RenderDoc API).
  - Tracy for CPU zones, GPU zones, lock contention and memory.
  - Crash dumps, plus GPU crash diagnostics: Nsight Aftermath (NVIDIA), Radeon
    GPU Detective (AMD), VK_EXT_device_fault, and your own breadcrumbs (write
    markers into a host-visible buffer with vkCmdFillBuffer and read the last
    one after DEVICE_LOST).
  - In-engine ImGui panels: memory per tag, job timeline, render graph view,
    physics debug draw, network stats.
  - Input recording and replay with deterministic seeds. Essential for physics,
    AI and network bugs.
  - Test on at least two GPU vendors regularly. NVIDIA is forgiving and hides
    bugs.

  Debugging method for the really bad ones

  1. Reproduce deterministically. Record inputs and seeds and replay them.
  2. Bisect. Use git bisect on commits, and toggle features at runtime (disable
     passes, systems or threads one by one).
  3. Shrink the surface. Single-threaded jobs, full barriers everywhere, the
     malloc allocator, CPU-only path.
  4. Check across vendors and builds. If it happens only on one GPU or only in
     Release, suspect sync, uninitialized memory or undefined behavior.
  5. Write the regression test (headless rendering to an image with diffing, or
     a physics scene snapshot) before fixing it.

❯ later on, I want my game engine to be platform-agnostic and RenderAPI
  agnostic (OpenGL, DirectX, Vulkan, ...)

● Making the Engine Platform- and Render-API-Agnostic

  This changes one recommendation from my previous answer. I said to build a
  thin Vulkan wrapper and not design for DX12/Metal yet. With your new goal,
  design the RHI (rendering hardware interface) to be backend-agnostic now, but
  implement only Vulkan at first. Then add a second backend early, around the
  render graph milestone, to prove the abstraction works. If you abstract late,
  you rewrite the renderer. If you abstract early but only ever test against one
  API, you get an abstraction shaped exactly like Vulkan that won't fit
  anything else.

  ---

  1. Choose the abstraction level: a "modern explicit" RHI

  Model the RHI on the common ground of Vulkan, D3D12 and Metal: explicit
  command lists, pipeline state objects, bindless resources, render passes
  declared up front. Then make older or simpler APIs emulate that model. Don't
  design around OpenGL or D3D11 semantics.

  Concept: Device / queue
  Vulkan: VkDevice, VkQueue
  D3D12: ID3D12Device, command queue
  Metal: MTLDevice, MTLCommandQueue
  OpenGL 4.5/4.6: implicit context
  ────────────────────────────────────────
  Concept: Command list
  Vulkan: VkCommandBuffer
  D3D12: ID3D12GraphicsCommandList
  Metal: MTLCommandBuffer + encoders
  OpenGL 4.5/4.6: emulated (record, then replay on the GL thread)
  ────────────────────────────────────────
  Concept: Pipeline
  Vulkan: VkPipeline
  D3D12: PSO

  About OpenGL: it is by far the worst fit. It's single-threaded, its state is
  implicit, and it has no real pipelines. Ask yourself why you need it. If the
  answer is the web, WebGPU fits the modern model much better. If it's old
  hardware, consider giving GL a reduced feature tier. I'd put GL last, or drop
  it.

  2. RHI design

  Rules that keep the abstraction honest

  1. No backend headers in public RHI headers. vulkan.h and d3d12.h are included
     only in rhi_vulkan/*.cpp and rhi_d3d12/*.cpp. Enforce it with CMake: the
     renderer links only against rhi (the interface).
  2. All resources are opaque handles (index + generation). Backends keep their
     own pools.
  3. Everything is created from descriptors (BufferDesc, TextureDesc,
     PipelineDesc). These are plain structs, easy to hash, serialize and cache.
  4. Abstract enums (Format, ResourceState, CompareOp, …) with translation
     tables per backend.
  5. Capabilities over assumptions. Query device->caps() for bindless, mesh
     shaders, ray tracing, async compute and max push constants, and have the
     renderer choose a path from that.
  6. The render graph owns synchronization. It emits abstract ResourceState
     transitions. Each backend maps them to real barriers, or ignores them
     (Metal, GL).

  Interface sketch

  // rhi/Device.h — no backend includes
  namespace rhi {

  enum class Backend { Vulkan, D3D12, Metal, OpenGL, WebGPU, Null };

  enum class ResourceState : uint32_t {
      Undefined, CopySrc, CopyDst, ShaderRead, ShaderWrite,
      RenderTarget, DepthWrite, DepthRead, Present, IndirectArg
  };

  struct BufferDesc  { uint64_t size; BufferUsage usage; MemoryType memory;
  const char* debugName; };
  struct TextureDesc { Extent3D extent; Format format; uint32_t mips, layers;
  TextureUsage usage; const char* debugName; };

  class CommandList {
  public:
      virtual ~CommandList() = default;
      virtual void barrier(std::span<const ResourceTransition>) = 0;
      virtual void beginRendering(const RenderingDesc&) = 0;
      virtual void endRendering() = 0;
      virtual void setPipeline(PipelineHandle) = 0;
      virtual void pushConstants(const void* data, uint32_t size) = 0;  // root
  constants / push constants / setBytes
      virtual void setIndexBuffer(BufferHandle, uint64_t offset, IndexType) = 0;
      virtual void drawIndexed(uint32_t indexCount, uint32_t instanceCount,
  uint32_t firstIndex, int32_t vertexOffset, uint32_t firstInstance) = 0;
      virtual void drawIndexedIndirectCount(BufferHandle args, BufferHandle
  count, uint32_t maxDraws) = 0;
      virtual void dispatch(uint32_t x, uint32_t y, uint32_t z) = 0;
      virtual void copyBuffer(BufferHandle src, BufferHandle dst, uint64_t size)
  = 0;
      virtual void beginMarker(const char* name) = 0;   // debug labels / PIX
  events
      virtual void endMarker() = 0;
  };

  class Device {
  public:
      virtual ~Device() = default;
      virtual const DeviceCaps& caps() const = 0;

      virtual BufferHandle   createBuffer(const BufferDesc&) = 0;
      virtual TextureHandle  createTexture(const TextureDesc&) = 0;
      virtual PipelineHandle createGraphicsPipeline(const GraphicsPipelineDesc&)
  = 0;
      virtual void destroy(BufferHandle) = 0;    // deferred internally until
  GPU is done
      virtual void destroy(TextureHandle) = 0;

      virtual uint32_t bindlessIndex(TextureHandle) = 0;  // shader-visible
  index
      virtual uint64_t gpuAddress(BufferHandle) = 0;      // BDA / GPU VA;
  caps-gated

      virtual SwapchainHandle createSwapchain(const platform::NativeWindow&,
  const SwapchainDesc&) = 0;
      virtual CommandList*    beginCommandList(QueueType) = 0;
      virtual SubmitTicket    submit(std::span<CommandList*>, QueueType) = 0;
      virtual void            present(SwapchainHandle) = 0;
      virtual void            waitIdle() = 0;
  };

  std::unique_ptr<Device> createDevice(Backend, const DeviceCreateInfo&);
  }

  Virtual calls are fine. One indirect call per command costs a few nanoseconds,
  which is nothing next to driver work. Keep the interface coarse: no per-state
  setters like setBlendMode, because state lives in pipelines. Compile in every
  backend available on a platform and pick one at runtime (via command-line
  flag or config), which makes A/B testing between backends trivial.

  Add a Null backend immediately

  rhi_null does nothing and returns valid handles. It is useful for:
  - dedicated servers, which matter for your networking milestone,
  - unit tests and CI without a GPU,
  - checking that game code never depends on a real GPU.

  3. Shaders: one source language, many targets

  This is the part people underestimate most.

  Recommendation: Slang. It compiles one source to SPIR-V (Vulkan), DXIL
  (D3D12), MSL (Metal), GLSL (GL) and WGSL (WebGPU), and it offers reflection.
  Alternative: HLSL → DXC for DXIL and SPIR-V, then SPIRV-Cross for MSL and
  GLSL.

  What makes cross-compilation work is a fixed binding convention, so each
  backend can map bindings mechanically:

  push/root constants   (≤128 bytes: draw index, material index, buffer
  addresses)
  space0 / set0         global bindless: Texture2D[], RWTexture2D[],
  SamplerState[], ByteAddressBuffer[]
  space1 / set1         per-frame constants (camera, time, lights)

  ┌────────────┬────────────┬──────────────────────────┬──────────┬──────────┐
  │ Convention │   Vulkan   │          D3D12           │  Metal   │    GL    │
  ├────────────┼────────────┼──────────────────────────┼──────────┼──────────┤
  │            │            │                          │ setBytes │ UBO at   │
  │ Push       │ push       │ root constants           │  /       │ binding  │
  │ constants  │ constants  │                          │ argument │ 0        │
  │            │            │                          │  buffer  │          │
  ├────────────┼────────────┼──────────────────────────┼──────────┼──────────┤
  │ Bindless   │ descriptor │ SM 6.6                   │ argument │ bindless │
  │ set        │  indexing  │ ResourceDescriptorHeap[] │  buffer  │  ext or  │
  │            │            │                          │ tier 2   │ arrays   │
  └────────────┴────────────┴──────────────────────────┴──────────┴──────────┘

  The offline cooker compiles every shader for every target and stores blobs per
  backend in the asset. Runtime compilation is only for hot reload.

  4. Coordinate-system conventions: unify them once

  Pick D3D/Vulkan conventions as the engine standard: depth range 0..1,
  reverse-Z, texture UV origin top-left, right-handed world. Then fix each
  backend at one point:

  ┌─────────┬────────────────────────────────────────────────────────────────┐
  │ Backend │                           Adjustment                           │
  ├─────────┼────────────────────────────────────────────────────────────────┤
  │ Vulkan  │ Negative viewport height (Y flip)                              │
  ├─────────┼────────────────────────────────────────────────────────────────┤
  │ D3D12   │ None                                                           │
  ├─────────┼────────────────────────────────────────────────────────────────┤
  │ Metal   │ None (same as D3D)                                             │
  ├─────────┼────────────────────────────────────────────────────────────────┤
  │ OpenGL  │ glClipControl(GL_UPPER_LEFT, GL_ZERO_TO_ONE) (GL 4.5). Gives   │
  │         │ D3D-style depth and origin, so no shader changes are needed    │
  └─────────┴────────────────────────────────────────────────────────────────┘

  Projection matrices are computed once in engine math and never #ifdef'd per
  backend.

  5. Platform abstraction

  GLFW covers Windows, Linux and macOS, but not mobile, consoles or the web
  (except through Emscripten). Treat GLFW as one backend of your platform layer,
  not as the platform layer.

  core/platform/          interface: Window, Input, FileSystem, Time,
  Thread/Fiber,
                          DynamicLibrary, Clipboard, Dialogs, CrashHandler,
  Sockets
  core/platform_glfw/     Window + Input on desktop
  core/platform_win32/    files, threads, crash dumps (MiniDumpWriteDump),
  sockets
  core/platform_posix/    Linux/macOS equivalents
  core/platform_android/  later (NativeActivity / GameActivity)

  The window must expose native handles for surface creation, because each RHI
  backend needs something different:

  namespace platform {
  struct NativeWindow {
      enum class Type { Win32, X11, Wayland, Cocoa, Android, Web } type;
      void* display;  // HINSTANCE / Display* / wl_display*
      void* window;   // HWND / Window / wl_surface* / CAMetalLayer* /
  ANativeWindow*
  };
  }

  Window creation also depends on the backend. Use GLFW_NO_API for Vulkan, D3D12
  and Metal, and request a context for GL. So the window gets created after the
  backend is chosen.

  Other places where platforms differ (they have to be correct from day 1):
  - File paths: use a VFS with /-separated virtual paths. Convert to native
    paths only inside the platform layer. Watch case sensitivity: Linux will
    break Textures/Rock.png vs textures/rock.png.
  - Text: UTF-8 internally. Convert to UTF-16 only at Win32 API boundaries.
  - Threads: std::thread is fine. Affinity, priorities, fibers and thread names
    are platform-specific, so put them behind the interface.
  - Sockets: Winsock vs BSD sockets. Hide them behind net/transport.
  - Compilers: build with MSVC and Clang (and GCC on Linux) from M0. Each
    catches different undefined behavior and non-standard code.
  - Endianness and alignment: cooked assets are little-endian, with explicit
    versioning.
  - Audio: miniaudio is already cross-platform.

  7. Debugging a multi-backend renderer

  - Golden-image tests: render fixed test scenes headless on every backend and
    diff them against reference images with a small tolerance. This catches most
    "works on Vulkan, broken on D3D12" bugs automatically.
  - Use each API's native tool: RenderDoc (Vulkan, D3D12, GL), PIX (D3D12, with
    the best GPU-crash and timing tools on Windows), Xcode GPU debugger (Metal),
    Nsight (Vulkan, D3D12).
  - Turn on every backend's validation: Vulkan validation + sync validation, the
    D3D12 debug layer + GPU-based validation + DRED (crash breadcrumbs), Metal
    API and shader validation, GL_KHR_debug.
  - Common cross-backend bugs:
    - Y-flipped or upside-down render targets, from inconsistent conventions
      (fix in one place, per section 4).
    - Different constant-buffer packing between HLSL cbuffers and std140. Use
      explicit packing and static_assert struct layouts.
    - Format support differences (e.g. some depth/stencil or BC formats are
      missing on mobile). Gate them through caps().
    - Barrier bugs hidden on Metal and GL, because those APIs synchronize for
      you. Vulkan and D3D12 are the strict ones, so test on them often.
    - Resources destroyed too early on one backend only: the
      deferred-destruction logic must be identical in shape across backends.

  5. A platform interface with GLFW as one implementation, plus CI on two OSes
     and two compilers.
  6. A second real backend (D3D12) right after the render graph, not "someday."

  - Put presets in CMakePresets.json (windows-debug, windows-release,
    linux-debug) so CI and your machine build the same way.

  domain), with one exception: FreeType is dual-licensed FTL/GPLv2, so choose
  FTL, which requires a credit line in your docs or credits. Keep a
  third_party/LICENSES.md listing each library and its license.

    .dmp, PIX/Nsight captures, and logs.

    .vscode/ files (settings, tasks, launch, extensions) are still tracked.

    shared .claude/settings.json are still tracked.

  - Build folders like /build/ and /Debug/ only match at the repo root.
    Otherwise a source folder such as engine/core/debug/ would be silently
    ignored.
  - third_party/ is not ignored, since submodules must be committed. Rules in
    this file don't affect what's inside the submodules anyway.
  - CMakePresets.json is tracked (shared presets); only CMakeUserPresets.json
    (personal overrides) is ignored.
